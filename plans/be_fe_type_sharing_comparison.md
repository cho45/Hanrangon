# Backend/Frontend データ構造共有手法の比較 (Go & TypeScript) - 改訂版

1人+LLM開発において、BE/FE間でデータ構造（型）を共有するための主な手法と、メンテナンス状況を考慮した Pros/Cons をまとめます。

## 手法比較表

| 手法 | 推奨ツール | Pros | Cons | メンテナンス性 / 備考 |
| :--- | :--- | :--- | :--- | :--- |
| **A. Go Struct to TS** | **[tygo](https://github.com/gzuidhof/tygo)** | GoのASTを解析してTS定義を生成。コメントも引き継げる。 | 型定義のみ。通信層の生成はない。 | ◎ 活発にメンテされている。 |
| **B. Connect (Protobuf)** | **[Connect-Go](https://connectrpc.com/)** | 通信層まで型安全。Protobufの定義から全て生成。 | 初期設定コスト。Protobufへの習熟。 | ◎ 非常に活発 (Buf社)。 |
| **C. OpenAPI** | **[oapi-codegen](https://github.com/oapi-codegen/oapi-codegen)** | 業界標準。ドキュメント生成。 | YAML管理のオーバーヘッド。 | 〇 安定しているが、1人開発には重い。 |
| **D. 手動共有** | (LLM) | 導入コストゼロ。 | 同期漏れのリスク。 | - |

---

## 詳細分析と再選定

### 1. tygo (手法 A) - 「型定義のみを共有したい」場合の決定版
- **特徴**: `typescriptify` の現代的な代替。Go のソースコード（AST）を直接読み取り、TypeScript のインターフェースを生成する。
- **Pros**: 既存の Go コードに特殊なタグを大量に書く必要がなく、設定ファイル (`tygo.yaml`) だけで制御可能。
- **1人+LLMへの適性**: 非常に高い。LLM に「このパッケージの型を TS に反映して」と頼むだけで済む。

### 2. Connect (手法 B) - 「通信層まで含めて堅牢にしたい」場合
- **特徴**: gRPC の良いとこ取りをした HTTP/JSON RPC フレームワーク。
- **Pros**: フロントエンドで `client.updateEntry({ id: 1, ... })` のように、まるでローカル関数を呼ぶように API を叩ける。
- **1人+LLMへの適性**: 高い。LLM は「生成されたクライアントのメソッド」を呼ぶだけでよく、エンドポイント URL や HTTP メソッドを覚える必要がなくなる。

---

## 結論：Hanrangon への最終推奨

メンテナンス状況と導入コストを考慮し、以下の2案を提案します。

### 案1：tygo による軽量な型共有（推奨）
- **理由**: 現在の Echo ベースのルーティングを維持したまま、最小限の労力で「型不整合」を防げるため。
- **アクション**: `tygo` を導入し、バックエンドの `model` や `app` にあるリクエスト/レスポンス用構造体を `admin-frontend/src/types/` に出力する。

### 案2：Connect への段階的移行
- **理由**: 将来的に API が増え、通信層のボイラープレート（fetch やエラーハンドリング）が苦痛になった場合の抜本的解決策。
- **アクション**: 新しい API から Connect で実装し、既存の Echo ハンドラを徐々に置き換える。

**結論**: まずは **tygo** を導入し、LLM がフロントエンドを書く際の「正確な型定義」を提供することから始めるのが、最もコスト対効果が高いです。
