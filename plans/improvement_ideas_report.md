# Hanrangon プロジェクト改善提案レポート (第3版)

現状のコードベースとアーキテクチャを分析し、ユーザーからのフィードバック（検索は LIKE で十分、1人+LLM 開発における OpenAPI 化のコスト対効果の疑問）を踏まえた改善アイデアを提案します。

## 1. 1人+LLM 開発における「型安全」の再定義

「1人+LLM」の開発環境において、ドキュメントとしての OpenAPI は確かに冗長かもしれません。しかし、**「LLM がコードを正確に理解し、フロントエンドとバックエンドの不整合を即座に指摘できる状態」**を作ることは、開発速度を維持するために重要です。

### 提案：OpenAPI の代わりに「共有型定義」の導入
OpenAPI 仕様書をフルで書くのではなく、以下のいずれかの軽量なアプローチを提案します。

1.  **Shared Types (TypeScript-friendly Go structs)**:
    - Go のリクエスト/レスポンス用構造体から TypeScript の型定義を自動生成するツール（`tkrajina/typescriptify-golang-structs` など）を導入。
    - LLM は生成された TS 型定義を見るだけで API の構造を理解でき、フロントエンド実装時の型エラーをコンパイル時に検知できます。
2.  **Connect (Buf.build) の検討**:
    - Protobuf で API を定義し、Go と TS のコードを生成。
    - メリット：OpenAPI よりも定義が簡潔で、LLM にとっても「定義ファイル」という明確なコンテキストを与えやすい。

## 2. 改善アイデアのカテゴリ分け

### A. 開発効率と信頼性 (DX)
1.  **型定義の自動同期 (B-1 改)**:
    - 上述の「共有型定義」により、バックエンドの構造体変更を即座にフロントエンドの型エラーとして可視化する。
2.  **データベースマイグレーションの自動化 (B-2)**:
    - **優先度：高**。`goose` などの導入により、スキーマ変更を `sqlc generate` と同様にコマンド一つで管理・適用できるようにする。
3.  **LLM 用コンテキストの最適化**:
    - `CLAUDE.md` や `GEMINI.md` を活用し、LLM がプロジェクト固有のルール（DB 分離の意図、ポストプロセスの仕組み等）を誤解しないための指示を整理する。

### B. ユーザー体験と機能改善
1.  **エディタのリアルタイムプレビュー (C-1)**:
    - `AppEditor.svelte` で、保存前にポストプロセス（MathJax 等）の結果を確認できるようにする。
2.  **画像のオンデマンド変換・配信 (A-1)**:
    - Cloudflare R2/Images を活用し、閲覧者のデバイスに最適な形式（AVIF/WebP）を動的に配信することで、転送量削減と高速化を図る。

### C. リソース管理の最適化
1.  **TF-IDF 更新のインクリメンタル化**:
    - 関連記事抽出の精度を維持しつつ、計算負荷をさらに抑えるためのロジック改善。

## 3. 優先順位付けと具体的なアクションプラン

### 優先度：高（1人開発の「守り」を固める）
*   **共有型定義の自動生成 (A-1)**: 手動で TS 型を書く手間を省き、LLM との協調をスムーズにします。
*   **DB マイグレーションツールの導入 (A-2)**: スキーマ管理のミスを防ぎます。

### 優先度：中（「攻め」の改善）
*   **エディタのプレビュー改善 (B-1)**: 執筆リズムを向上させます。
*   **画像の配信最適化 (B-2)**: サイトパフォーマンスを向上させます。

## 4. 結論

1人+LLM 開発においては、**「LLM が迷わないためのメタデータ（型定義やマイグレーション履歴）」**を自動生成する仕組みを作ることが、最もコスト対効果の高い投資となります。OpenAPI という「重いドキュメント」ではなく、**「動く型定義」**を共有する軽量なアプローチを推奨します。
